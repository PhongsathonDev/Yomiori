# การใช้ผลสแกนซ้ำ — WF-0018

28 October 2026 · เปรียบเทียบกับ [baseline WF-0011](report.md)

## ทางเลือก

- สแกนไฟล์ทุกครั้ง: ตรวจการเปลี่ยนจากภายนอกได้ในการสแกนถัดไป และไม่เก็บ summary แต่ยังอ่าน 1,000 ไฟล์ต่อรอบใน fixture 1,000 ตอน
- เก็บ summary เฉพาะ process พร้อม revision: เลือกแนวทางนี้ เพราะลดการอ่านซ้ำโดยไม่สร้าง index ถาวรที่อาจไม่ตรงกับไฟล์จริง เก็บ metadata รายตอนและสถานะรูปเท่านั้น ไม่เก็บเนื้อหาบท หน่วยความจำจึงเพิ่มตามจำนวนตอน แต่ยังไม่มีตัวเลขบน Android
- index ถาวร: อาจลดงานแม้เริ่ม process ใหม่ แต่ต้องดูแลความสอดคล้อง การกู้หลังเขียนขัดจังหวะ และตรวจไฟล์ภายนอก; ไม่เลือกเพราะต้องตรวจไฟล์จริงเมื่อเริ่ม process ใหม่อยู่แล้ว

revision เปลี่ยนเมื่อแอปเขียน ลบ ล้าง หรือบันทึกรูป; generation ป้องกันงานเก่าหลังล้าง สแกนที่ซ้อนการเปลี่ยนจะลองใหม่ ไฟล์จริงและ backup ยังเป็นแหล่งข้อมูลอ่านตอน ผลที่พบ I/O error ไม่ถูก cache แม้จะคืนผลบางส่วนชั่วคราว การแก้หรือทำไฟล์เสียจากภายนอกระหว่าง process อาจไม่ปรากฏในรายการจนเริ่ม process ใหม่ ตามที่ผู้ใช้ยอมรับใน WF-0012

## ผลและข้อจำกัด

รัน `npm run benchmark:scan` ด้วย fixture และ harness เดียวกับ baseline: 1,000 ตอน clean รอบแรก `getSavedLibrary` list 5, stat 1,000, read 1,000; รอบสอง list 1, stat/read 0 เทียบ baseline ที่ทั้งสองรอบอ่าน 1,000 ไฟล์ สำหรับ mixed รอบแรกอ่าน 1,024 ครั้ง รอบสองอ่าน 0 ครั้ง รวมกรณี backup การวัด entry ของ harness นี้ตามหลังการสแกน storage จึงเป็น warm cache ไม่ใช่ cold entry เทียบตรงกับ baseline ไม่ได้

ตัวเลขเป็น operation ของ mock บน desktop ไม่ใช่เวลา Android หรือหน่วยความจำจริง งาน [ตรวจ APK สุดท้ายบน Android จริง](../../issues/WF-0008.md) ต้องวัดทั้งเวลาและหน่วยความจำตามขนาดคลังจริงก่อนกำหนดเป้าหมาย ไม่สร้าง APK ระหว่างทาง

Regression tests ใน `reader-mobile/__tests__/offline.test.ts` ครอบคลุมเขียน อัปเดต ลบ ล้าง รูป backup สแกนซ้อนการเปลี่ยน อ่านพร้อมกัน และ I/O ล้มเหลวแล้วกลับมา; `npm test` ผ่าน 87 tests, `npm run typecheck`, `npm run lint`, `npm run benchmark:scan` ผ่าน รอบแรกของ full test มี timeout ใน reader UI แต่รันซ้ำทั้งชุดผ่าน
