## Destination

ได้สเปกพร้อมนำไปพัฒนา Reader Mobile สำหรับใช้เองบน Android: เปิดแอปและเข้าถึงเนื้อหาที่มีในเครื่องโดยไม่รอเครือข่าย หาตอนที่ดาวน์โหลดเจอเสมอ และมีข้อมูลกับทางลัดในหน้าอ่านครบพอดี พร้อมเกณฑ์ตรวจบนมือถือของผู้ใช้และไม่มีการตัดสินใจสำคัญค้างอยู่

## Notes

- ผู้ใช้คนเดียว ใช้ส่วนตัว Android ก่อน เลือกดาวน์โหลดตอนพร้อมรูป ไม่ใช่แผนเปิดให้บุคคลภายนอกทดสอบหรือขึ้นสโตร์
- หน้าอ่านเป็นพื้นที่ออกแบบหลัก อนุญาตพิจารณาจุดรอข้อมูลตอนเปิดแอปและทางเข้าจากชั้นหนังสือ/สารบัญเฉพาะที่จำเป็นต่อเป้าหมาย ไม่ใช่ redesign ทุกหน้าจอ
- อาการจากผู้ใช้: APK ที่ติดตั้งเป็นรุ่นก่อนหน้า หน้าโหลดตอนเปิดแอปช้าเมื่อมีเน็ต แต่เร็วเมื่อไม่มีเน็ต; บางตอนที่เคยดาวน์โหลดไม่ปรากฏ; UI รู้สึกโล่งหรือขาดบางอย่าง แต่ยังไม่มีรายการฟีเจอร์ที่ยืนยัน
- ผู้ใช้เลือกเป้าหมายสามข้อใน Destination แล้ว ข้อเสนอ UI ต้องตอบเป้าหมายนี้ ไม่แปลงคำว่า “โล่ง” เป็นรายการฟีเจอร์เพิ่มโดยอัตโนมัติ
- Source baseline: `97e09a0` มีงานแคช/ดาวน์โหลด/progress และ tests 38 เคสแล้ว ผลเหล่านี้ไม่ใช่หลักฐานว่า APK รุ่นเก่าหรืออุปกรณ์จริงทำงานเหมือน source ล่าสุด
- หลักฐานใน source: [Reader loading](../../reader-mobile/src/screens/ReaderScreen.tsx), [chapter discovery](../../reader-mobile/src/services/api.ts), [saved files and stats](../../reader-mobile/src/services/storage.ts), [device validation](../../reader-mobile/VALIDATION.md)
- Source ล่าสุดแสดงชั้นหนังสือจากข้อมูลในเครื่องก่อน แต่ยังมีช่องที่ไฟล์ตอนอยู่จริงโดยไม่ถูก enumerate และมีบางเส้นทางรอเครือข่ายก่อนใช้ bundled fallback ทั้งสองข้อเป็นสิ่งที่ตรวจจากโค้ด ไม่ใช่คำวินิจฉัย APK ของผู้ใช้
- ก่อนเริ่ม baseline `app.json` ระบุ version `1.0.0` / Android versionCode `1`; การ push ปัจจุบัน deploy เฉพาะเว็บ ไม่ได้อัปเดต APK บนมือถือ งานเตรียม baseline เปลี่ยนเป็น `1.0.1 (2)` แล้ว แต่ build ถูกยกเลิกตามความต้องการผู้ใช้ ยังไม่มี APK ใหม่และยังไม่มีผลทดสอบบนเครื่องล่าสุด
- ความต้องการล่าสุด: ไม่บิลด์ baseline ระหว่างทาง ใช้การตรวจ source, Typecheck, Lint, automated tests และ preview ที่ไม่ต้อง cloud build ระหว่างแก้ไข บิลด์ APK เมื่อแก้ครบพร้อมตรวจครั้งสุดท้ายเท่านั้น เก็บ native/performance validation ที่ทำแทนมือถือไม่ได้ไว้ใน checklist ท้ายงาน ไม่ให้ผลจาก APK ใหม่เป็น prerequisite ของการวางแผน/แก้โค้ด
- งานนี้เป็นการวางแผนและตัดสินใจ ไม่ implement ฟีเจอร์ระหว่าง charting; task ticket อาจเตรียม build/เก็บหลักฐานเพื่อให้ตัดสินใจได้ ต้องรักษาข้อมูลเดิมและไม่ถอนแอปหรือล้างข้อมูลโดยถือว่าได้รับอนุญาตแล้ว
- ทุก session อ่านทักษะ wayfinder; grilling ใช้ร่วมกับ domain-modeling; งานพิจารณา UX ใช้ frontend-design และ impeccable โดยยึด Android native affordances และเนื้อหานิยายจริง Prototype ต้องมีผู้ใช้ตอบรับด้วยตนเอง
- ตรวจแล้วว่า environment นี้ยังไม่มี supporting skills ชื่อ `prototype` และ `research` ไม่มี research ticket ใน frontier นี้ ก่อนเริ่ม ticket ประเภท prototype หรือเพิ่ม research ต้องจัดหา skill ที่จำเป็นหรือให้ผู้ใช้เลือก workflow ทดแทนก่อน ห้ามแสร้งว่าได้ใช้ skill ที่ไม่มี ข้อนี้ไม่ขวางการ chart map หรือการทำ task/grilling ที่พร้อมอยู่
- ความสัมพันธ์ child และ blockers ดูผ่าน local tracker ตาม [Wayfinding operations](../README.md) ไม่เก็บ open-ticket index ซ้ำใน map

## Decisions so far

ยังไม่มี ticket ที่ resolve ใน map นี้ ข้อมูลที่ผู้ใช้ระบุระหว่างกำหนดปลายทางอยู่ใน Notes

## Not yet specified

- รายละเอียดด้าน typography ภาพประกอบ และการเปิด/ซ่อน controls ที่จะมีผลหลังผู้ใช้เห็นต้นแบบ ยังไม่กำหนดหน้าตาหรือฟีเจอร์จากความรู้สึกว่า UI โล่งเพียงอย่างเดียว
- ปัญหาด้านการอ่านเพิ่มเติมที่อาจปรากฏจากบิลด์ล่าสุดบนเครื่องจริง จะตั้งคำถามใหม่เมื่อมีหลักฐานพอ ไม่ตั้งสมมติฐานว่าอาการทั้งหมดมาจาก network หรือ rendering

## Out of scope

- [สร้างฐานเปรียบเทียบการเปิดแอปบน Android](WF-0002.md): ไม่สร้าง APK baseline ก่อนแก้ไข เพราะ EAS ใช้เวลานานและผู้ใช้ต้องการบิลด์เมื่อแก้ครบ Build ที่ส่งถูก cancel สำเร็จ ไม่ถือว่าได้หลักฐานบนอุปกรณ์แล้ว
- ผู้ทดสอบภายนอก ระบบสมัคร การขึ้น Play Store/App Store และการเปิดให้บริการสาธารณะ: แอปนี้ใช้เอง
- iOS และ redesign ของ reader-web: รอบนี้ Android
- Redesign ชั้นหนังสือ/หน้ารายละเอียดทั้งหน้า ระบบสมาชิก/ซิงก์ข้ามเครื่อง และฟีเจอร์ community ใหม่: ไม่ใช่เป้าหมายหน้าอ่านรอบนี้
- Bundling ทุกเรื่องทุกตอน: ผู้ใช้เลือกดาวน์โหลดตอนพร้อมรูปตามต้องการ
- เปลี่ยน navigation หรือ virtualization เป็นข้อสรุปล่วงหน้า: ต้องมีหลักฐานและเหตุผลจาก ticket ก่อนจึงพิจารณา
